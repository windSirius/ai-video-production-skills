# 旧项目迁移

旧项目只在需要续做时迁移。已经交付且不再修改的项目保留原目录即可，不为形式统一重写历史。

## 迁移原则

1. 先只读盘点所有可能的脚本、独立口播、SRT、A/B/C、BGM、最终视频和封面。
2. 使用实际文件SHA，不根据`最终版`、`v3`、修改时间或旧`CURRENT.json`猜测权威。
3. 只有用户曾明确批准且能够对应到具体文件时，才登记审批。缺少文件身份或展示顺序的旧聊天只记为迁移备注。
4. 机器QA存在不等于人工批准；文件存在不等于阶段完成。
5. 先确定最早不可信阶段，再从该阶段进入新状态机。后续产物可保留在磁盘，但不登记为当前交付。

## 常见映射

- 已批准脚本、配音和最终字幕均可确认：从第七阶段开始。
- 配音机器检查通过，但没有完整人工试听：停在第五阶段`awaiting_user`；已有字幕登记为候选，不进入权威。
- A/B/C分别通过，但没有包含真实旁白、字幕和BGM的完整整合代理：停在第九阶段。
- 2K60独立母版存在，但最终整合视频没有重新验收：停在第十一阶段。
- 最终视频存在，但封面选择或多画幅未完成：停在第十二阶段。
- `CURRENT.json`与实际产物冲突：先让用户确认，不自动迁移成`sealed`。

## 旧工具

旧workflow v2/v3、Harness、批次账和复杂审核器只作为历史证据，不复制进新项目。需要引用旧QA时，把它登记为一个普通证据文件；不要让旧状态机与新`CURRENT.json`同时生效。

本仓库保留早期 `harness.py`、`run_objective_checks.py` 与相关测试，供既有 `run_manifest.json` 工程和剪映兼容模块继续使用。它们不是新十三阶段流程的入口。识别到这类旧工程时，先按原冻结契约只读核验；用户明确要求迁移后，再按本页原则建立新状态。不得把旧 Harness 的阶段封印直接转换成新 `CURRENT.json` 的产物审批。
