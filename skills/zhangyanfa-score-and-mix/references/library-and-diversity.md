# 曲库发现、跨期复用与试听

适用于新一期候选或用户要求扩充曲库。已批准的旧项目保持原审批和文件；本规则不授权返工、迁移或清理旧媒体。

## 共享资料与文件身份

从统一工作区 `00_管理/BGM曲库/入口.json` 读取 BGM 曲库位置；跨设备先核实实际原件路径。共享 `catalog.json` 保存原件引用与技术信息；`usage_history.json` 保存各期实际展示候选和最终选曲，分别计数。发布或播放数据不影响这两类事实。

- 曲目：`track_id`、`composition_id`、曲名/作者/专辑、真实 path/SHA、时长、配器 `palette`、叙事用途 `suggested_roles`、能量、歌词/人声情况、来源页、许可/署名、分类依据、试听状态。
- `track_id` 区分音频版本；`composition_id` 标识同一作品。去旋律版、不同码率、裁切和改名都不能增加作品数。仅标签自动生成的作品身份是暂定值，进入短名单前核对作者/曲名与别名。
- 历史：按制作顺序排列 `episodes`，每项有 `episode_key`、`candidate_track_ids`、`selected_track_ids` 及原 manifest/审批引用。缺失历史记明范围，不按文件修改时间猜最终选曲，不把所有候选都写成“使用过”。
- 管理索引不装音频副本；原有音乐原位引用，新曲在原始素材库按 source ID 登记。仅选用曲目在渲染时解码，不提前把整库扩成 WAV。

索引显式指定的音乐目录，避免扫描整个用户目录或无关私密音频：

```bash
python3 scripts/index_bgm_library.py \
  --directory MUSIC_FOLDER --metadata VERIFIED_SOURCE_RECEIPTS.json \
  --output CATALOG.json
```

`--metadata` 接受含 `tracks` 数组的 JSON，可多次传入；可传上一版 catalog 保留人工整理字段。命令只探测文件，不声称完成听审。

## 原有曲库评估覆盖

先盘点显式音乐目录和已登记的原曲；成片 BGM 母带、不同转码和重复副本不算新作品。保留原曲位置与稳定 ID，同时读容器和音频流标签；上传者不自动当成作者，文件名中的版本线索不能被通用曲名覆盖。标出容器与扩展名不符等可播放性问题，原件不为建库改名。

区分 `metadata_only`、`audio_checked`、`audition_ready` 和 `human_reviewed`；自动检测、生成试听、人工听过与用户通过是不同事实。分类器输出只能作为人声/配器线索，未检出人声不能证明纯器乐，不能按曲名猜配器。保存分类依据、具体待核点、实际音频范围与完整原曲入口。

用户要求整库盘点时，逐首提供可播放的配乐单听与同旁白、同范围、可比电平的对照；短曲可覆盖重叠范围，须明示。用已批准旁白做曲库校准不构成旧项目返工，也不新增旧期候选/选曲事件。试听派生文件走现有 resolver，目录和用途登记在共享曲库入口。后续仅补新文件或改变的版本，不要求每一期重听整库。

有人声的曲目也评估开场、无旁白间奏、转折或收尾职责；短 OST 也评估章节提示和过渡，不因不能循环整篇就静默排除。未选用写具体原因；尚未评估、待确认版本、人声遮蔽风险和确实不合题分开记录。是否是近期新选择按候选历史判断，与文件下载日期无关。

## 从叙事职责找曲目

先根据本期钩子、密集证据、转折、情感结尾写需要什么，再按这些职责检索整个目录。可搜索调查脉冲、古老仪式、寒冷空旷、亲密独白、机制演算、揭示或希望等方向；这些是检索维度，不是每期必须凑齐的风格。

先看未充分使用的本地原曲，再补与缺口有关的作者直供曲、游戏官方主题或已获准的生成音乐。是否具备发布条件单独核验，不能因为下载成功或它是 OST 就当作已授权。对于有署名条件的曲目，随交付提供可直接使用的署名清单。

默认先评估 12 首不同作品，再设计 house style 规定的四套候选；至少三首主曲未在最近三期候选中出现，最近三期实际选中的作品最多保留一首。四套主曲应涵盖至少三类实际配器，避免四首相近的钢琴氛围曲假装成四种方向。

这些是解决候选收缩的编辑默认值，不是为了凑数牺牲贴题。固定角色主题、连续专题、用户指定单曲或真实可用素材不足时，记录 `policy_reason` 或具体 `exceptions`；不能为了消掉红字编造配器、历史、作品身份。新作品身份和实际源曲 SHA 一致是不可用例外绕过的要求。

## 发现计划与实际候选绑定

本期 `tracks/vNNN/BGM` 中保存 `bgm_discovery.json`，并复制小型曲库/历史 JSON 作为该次决策快照，避免以后增加一首曲子就改变旧收据。

```json
{
  "schema": "bgm_discovery_v1",
  "shortlist": [
    {"track_id": "catalog_track_id", "fit_reason": "稀疏低音用于引文段，主旋律不会持续抢占专名"}
  ],
  "candidates": [
    {
      "candidate_id": "BG_A",
      "lead_track_id": "catalog_track_id",
      "track_ids": ["catalog_track_id"],
      "rationale": "解释这套方向如何服务本期核心判断",
      "evidence_strategy": "明确证据段如何减薄或留白",
      "turn_strategy": "明确反转和结尾如何变化"
    }
  ],
  "exceptions": []
}
```

示例仅说明字段；实际填完整短名单与全部候选。含有歌词、合唱、效果人声或未核实人声的方案补 `vocal_review`，说明语义和旁白遮蔽的核查结果。

```bash
python3 scripts/audit_bgm_diversity.py \
  --catalog catalog_snapshot.json --history history_snapshot.json \
  --plan bgm_discovery.json --review-manifest bgm_review_manifest.json \
  --output bgm_diversity_audit.json
```

首次设计时可省略 `--review-manifest` 做内部预检；对外提交时必须再次带入真实 manifest。报告绑定实际输入 SHA，复查候选 `checkpoints` 的源曲 SHA 或 `source_ids`。源曲与计划不符、同曲多版本冒充不同方向、源文件缺失/被改动时先修正，不向用户提交假多样性。自动统计只证明声明的分类与身份一致，不证明听感差异。

所有方案用同一段旁白、同一组钩子/密集证据/转折/结尾区间、可比电平试听。组合方案应在这些样段里展示所有拟选曲，不能审批后添加未听过的音乐。A 只是本期候选编号，不固定对应熟悉旧曲。

用户选曲后把“被展示”和“被选中”分别回写共享历史，并保留本期快照。整片审看沿用现有流程；不增加一次重复选曲审批。
